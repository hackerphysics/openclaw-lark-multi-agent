# 1.8.10 candidate — live input dispatch and yielded result custody

Local candidate only; publication and runtime activation are separate actions.

## Correctness changes

- A trusted exact-root Gateway `chat.final` with `yielded:true` synchronously preserves the original result observation and Feishu delivery target, then retires its foreground collector. The acknowledgment does not claim a final key, mark DONE, abort the task or replay input.
- New human inputs consult live public Gateway activity, not only an in-memory queue promise. A yielded task can keep its durable exact observer while a positively idle session receives a new ordinary request. For an uncached old root without yield, complete positive current-session history and exact local owner/batch/session-generation guards can release dispatch independently of task settlement.
- With no local owner, a publicly identified active Gateway root receives callback-confirmed insertion rather than another ordinary run. Missing activity/root identity remains durable unbound custody with paced read-only recovery; it is not fabricated admission or acceptance.
- Only proven never-attempted/no-effect insertions can return to ordinary input. Attempted/unknown and accepted inputs are never blindly replayed and do not monopolize later independent requests.
- Long silent tools/API calls and ten-minute presentation pauses are not yields or task-lifetime limits. Admission, batch changes, late callbacks, stop, reset and session-generation changes remain fenced.
- Late original-root results use their original durable trigger target. Publicly verified child/parent task lineage selects the old root; only its exact committed terminal reply is delivered, never tool input or an unverified child draft. Silent/empty/error outcomes settle only their attributable input obligations.
- The prolonged-unknown insertion reminder uses real time since the first unknown observation, persists its intent and outbox row in one transaction, and rechecks the current insertion/stop/session verdict before a platform effect.

## Runtime plugin verification

The coordinated `lma-core` plugin remains **0.2.0**; this bridge candidate does not require a new plugin implementation. Installing files or receiving `lma.core.capabilities` is not evidence that the dedicated insertion methods are active.

After activation through the Gateway-supported plugin control path, run:

```sh
lma check-core-plugin
# or, in the source checkout:
bash scripts/update-lma-core.sh --check
```

These read-only checks call the actual `lma.steer.capabilities` endpoint and require protocol 2, durable attempts, acceptance callbacks and session-generation binding. They do not submit a model/input request and do not claim model consumption, final-effect atomic CAS or platform delivery.

## Boundaries

An SDK acceptance callback is an acceptance receipt, not proof that a model consumed that message. Unknown outcomes retain their no-replay fence. Missing public lineage is not invented; unrelated proactive runs keep their existing generic route rather than borrowing a new human trigger. Offline WS/SDK/SQLite regression results are not real model/Feishu or Windows runtime canary evidence.
