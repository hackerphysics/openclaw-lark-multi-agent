# 1.8.5 — reliability candidate (not published)

- Long silent tools/API calls have no LMA 24-hour failure horizon. Ten-minute
  silence changes presentation only; exact-run custody survives disconnect and
  process restart in LMA-owned SQLite. Queries have short independent deadlines.
- Superseded observers transfer exact-run delivery custody synchronously. Failed
  replacement admission leaves a healthy old collector alive. Admission, owner,
  actual batch and persistent stop generations fence late work and UI updates.
- Inbound requests start with Typing. Get requires actual accepted custody, never
  local queueing, send initiation, a boolean eligibility value or `in_flight`.
  DONE belongs to the exact settled task. UI API failure is independently retried
  and cannot block admission or result delivery.
- Body, file/image/document and supplemental outputs share durable platform
  operation receipts and atomic context/checkpoint registration. Unknown platform
  outcomes fence retry/fallback. Exact platform IDs deduplicate echoes; independent
  identical-text tasks remain distinct. Confirmed partial chunks are recoverable.
- Historical context preview/explicit registration (never resend):
  `node scripts/audit-delivery-context.mjs --db <explicit-path> --bot <name>`.
  `--register --outbox <id> --chat <id> --verified-message-id <actual-id>` requires
  independently verified receipts. Upgrade does **not** auto-backfill live history.

## Persistent real-time insertion (coordinated bridge + lma-core 0.2.0)

- Busy-session inputs reserve durable message custody before ingress awaits.
  Short submit/query RPCs and one paced bridge recovery scheduler retain the
  original input beyond 3/8 seconds and hours of not-ready observations. There
  is no insertion age deadline or automatic ordinary-send timeout fallback.
- The production plugin now actually invokes the **public**
  `queueAgentHarnessMessage(..., { onQueueAccepted })`. Only the backend's
  `onQueueAccepted(true)` is persisted as acceptance and drives Get. Immediate
  SDK `true` means an attempt, not a receipt. SDK `false` or explicit callback
  `false` is a no-effect refusal and permits paced retry of the original target.
- Stable input ID + payload/session-generation/run/stop identity and fsynced
  plugin attempt journal make late callbacks queryable after RPC timeout or
  disconnect. Restart preserves accepted/unknown. Missing callbacks, missing
  journals after a possible attempt and crash ambiguity stay **unknown**, never
  ordinary-replayed; `queueIdentity` is NOT assumed to deduplicate host effects.
- Canonical bot/session generation, archive/reset and persistent stop epochs
  fence admission and reactions. Lifecycle + public exact-terminal observations
  prevent a known ended original run from being SDK-retargeted to its successor.
  Only an input proven never dispatched to the backend, with confirmed original
  terminal and session idle, is explicitly handed back to the ordinary queue
  once, with a status notice. Successor runs in the same session are legitimate
  session work, not a different chat; they are not silently selected by retries.

### Honest public-runtime boundary (not a feature-disable gate)

`atomicRunBound` remains **false**: public SDK resolution plus queue invocation
is synchronous locally, but the host offers no portable final-effect original-
run CAS across awaited backend preparation. We do **not** claim that stronger
host guarantee or model consumption. It is not a prerequisite for the user's
current-session input semantics, so builtin insertion is enabled with truthful
callback receipts instead of being universally `capability_blocked`.

Both inspected builtin versions implement the acceptance callback. A legacy or
alternative backend that never calls it remains **acceptance unknown** with no
Get/no automatic resend. Real public-SDK typed synthetic-harness and application
integration tests execute queue methods; these are offline transport conformance,
not live model/Feishu acceptance or proof that every optional backend supports
callbacks. No private SDK imports, synthetic authority, host DB edits or system
installation changes are involved.

This coordinated protocol candidate requires the matching bridge and lma-core
plugin. This file is release preparation, **not permission to publish, deploy or
restart anything**.
