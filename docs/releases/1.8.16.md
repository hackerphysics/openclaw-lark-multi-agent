# 1.8.16 — accept new input independently of background activity

## User-facing repair

Receiving input is different from starting execution. Ordinary sends already explicitly select noninterrupting `followup`; this release adds an independent guarded admission path rather than requiring the entire session to become globally idle.

- Aggregate activity, retained/queued/hidden pending records and maintenance work no longer act as a blanket receiving veto when the bridge can establish matching physical-session, observed-leaf and nonarchive evidence.
- Genuine injectable foreground targets retain SDK priority. A verified zero-effect/not-ready input can take one guarded followup path even when an observed foreground ID remains. Accepted/unknown/stopped or explicitly ineligible/target-changed input is never blindly replayed.
- Preserve the earliest genuinely observed leaf and let the public host CAS accept exact/ancestor progress or refuse an off-path branch. Normal background transcript advance is not treated as permanent session-generation failure.
- Preserve the existing bounded ordinary rescue for a fresh, never-attempted input whose activity state is genuinely unknown. An unknown submission receipt remains a different no-replay state.
- Guard refusal retains the latest input and gives a visible explanation. Restricted sends never auto-unarchive and retry. Stop, owner, actual batch, admission epoch, identity and source checks fence late reads/ACKs and concurrent handlers.
- Local scheduler retirement retains the original exact-run recovery, delivery target and honest Get state; it does not abort a business tool, invent a terminal outcome or infer input consumption.

## Parent final-review corrections

- Guarded same-proof backlogs respect configured message-count and byte bounds. Unselected inputs stay durably queued for subsequent bounded batches instead of being dropped or packed into an oversized request. One individually oversized input is not silently discarded.
- Gateway-accepted guarded inputs transition to ordinary, synchronize and clear their pending trigger in one SQLite transaction. This prevents an accepted input reappearing in later group catch-up context and preserves unknown custody if the local checkpoint fails.

- Parent exact-source full offline suite: **65 files / 1763 tests passed**. Includes 51 new candidate admission cases plus parent backlog byte/count and atomic checkpoint rollback controls, all prior collector/privacy/presentation tests, and the original six A4 tests with unchanged assertions.
- Bridge/all bundled-plugin builds and public SDK type contract passed. Package contents inspected; runtime dependencies and coordinated lma-core protocol/package remain unchanged (protocol 2 / 0.2.0).
- Static parent verification of the actual Windows OpenClaw **2026.9.6** public leaf helper confirmed the same requested-session exact-or-ancestor semantics as Linux **2026.9.9**. No private helper was imported/executed and no Core/config file was changed.
- Gateway acceptance is not immediate execution, per-input consumption or a platform receipt. Native FIFO, capacity/overflow, permissions, disconnect and stop behavior remain host constraints. Missing physical/leaf/nonarchive proof gets honest local custody, not a fabricated successful admission.
- Update bridge runtime only, with a coherent bridge-state backup and verified rollback. No session reset/history deletion, queue clearing, automatic revival of stopped work or Gateway restart is required.
- Original-group post-activation human input -> Gateway admission -> platform-accepted reply remains a separate live acceptance gate. Green offline tests, a version string and service readiness do not prove that gate.
