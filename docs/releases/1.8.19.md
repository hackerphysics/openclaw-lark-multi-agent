# 1.8.19 — Recover trusted bot identity after startup network failures

Fixes a long-lived group-only silence condition: a failed startup bot-identity
lookup could leave @bot messages unrecognized indefinitely while private chat
continued to work. The weakness also existed before 1.8.18.

## Recovery and safety

- Use authenticated original-account `GET /open-apis/bot/v3/info/`, never display
  names or user-supplied mention metadata to discover self identity.
- Apply a 2-second discovery bound, cancellation through authentication and info
  requests, single-flight ownership and paced 5-second-to-5-minute retries.
  Startup and private traffic remain available while discovery is unavailable.
- Hold fresh unresolved open-ID mentions before irreversible dedup/routing.
  Custody is bot/app/chat scoped and pinned to the originally observed physical
  session. Missing original proof is not permission to bind a later session.
- Recover verified targets through existing routing and input custody. A long
  model run no longer blocks later retained help/stop or another chat. Preserve
  stop/recall/expiry/close and session-generation/archive guards across awaits,
  queued handoff and restart. Transient journal errors have owned, paced repair.
- Refuse malformed/conflicting identity fields; preserve app-only proof, private
  isolation, @all and normal known-identity routing. Already processed historical
  inputs are not replayed. Legacy ACKs without sessionId keep durable target pins.

## Explicit boundaries

Unresolved custody is capped at 100 events per bot/app, 64KiB per event and 15
minutes. It is not Gateway acceptance, Get or DONE. Expired/fenced inputs never
execute automatically. A crash after dedup transfer can lose an input rather than
risk duplicate execution. A transport that ignores cancellation retains one raw
request slot instead of accumulating replacements.

Held mutating `/go` commands refuse with an explanation and require a fresh
post-recovery command; they do not initialize a successor supervisor. Legacy
reset/compact interfaces use late read checks, not a claimed atomic distributed
CAS absent from the backend schema. Ordinary chat/model operations use supported
physical-session guards. No new plugin protocol or Gateway configuration change
is required for the identity repair.

## Upgrade and validation

Build and test locally; transfer verified runtime artifacts only and preserve
compatible native dependencies. Back up bridge data before the additive custody
migration. Bridge activation is required; Gateway restart/session reset/history
cleanup is not. Do not replay older ignored commands to validate the upgrade.

Release gates: bridge/all bundled plugin builds, public SDK type contract and
67-file / 1889-test offline suite, including 94 identity recovery cases, on clean
exact-lock Node 24.19 and Node 26 environments. Platform activation and fresh
original-group human acceptance remain separate checks.
