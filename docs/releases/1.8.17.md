# 1.8.17 — Close linked insertion status cards after the original-chat reply

Presentation-only correction to 1.8.16. A legacy insertion's independent queued
card can now compact to **关联轮次已回复 / Linked run replied** when the exact
associated run has a complete, platform-confirmed final reply in the same
Bot/application/chat/stop epoch. Elapsed time uses delivery time, not repair time.

This is deliberately **not** proof that the inserted input was committed,
consumed or completed. No insertion acceptance, Get/DONE, model-sync, ordinary
admission, task execution, business replay or delivery custody semantics change.

- Require exact message identity, input timestamp, run/session compatibility and
  all accepted members of a coalesced cohort; reject incomplete/unknown delivery,
  nonfinal/error/verbose notices, foreign roots, old epochs and earlier replies.
- Seal all eligible card cohorts before asynchronous effects, so a new input is
  never silently included in a closing card. Preserve a card already containing
  the actual business answer rather than replacing that answer with a status.
- Recover known cards after restart from durable original-chat SDK receipts.
  Persist desired versus rendered UI status separately. Proven-zero-effect edits
  may retry with bounded backoff; attempted/unknown effects remain fenced.
  Successful edit receipts survive local journal-write failures without another
  transport call.
- No schema migration, Core/plugin or Gateway configuration change is needed.
  Bridge activation is needed; preserve runtime native dependencies and existing
  business/insertion records. Do not replay or reset sessions to repair a card.

Validation: bridge and all bundled plugin builds; public SDK type contract;
complete offline suite **66 files / 1789 tests passed**, including 26 linked-card
regressions and existing insertion-honesty/no-replay tests. Live activation and
original-card platform acceptance are separate deployment gates.
